---
description: Adversarial Claude × Codex review of a markdown file or GitHub PR (resumable, citation-checked).
argument-hint: "<PR#|file.md> [--comment] [continue]"
---

Invoke the adversarial-review workflow using the Workflow tool.

Parse $ARGUMENTS to extract the target (and optional flags):
- A number (e.g. "242") → a PR number
- A file path (e.g. "docs/architecture.md") → a file path
- If the user says "continue"/"approve more rounds"/"resume", pass `resume: true` (and `maxRounds` higher than before)
- If the user is answering a prior `needs_human` question, pass `resume: true` and `humanAnswer: "<their answer>"`
- Optional `effort` (`low`|`medium`|`high`|`xhigh`|`max`) and `model` tune the Codex run. Omit them to use the defaults: model **`gpt-5.6-sol`**, effort **`high`** for both PRs and files (high reasoning on a large file is ~30 min / ~700k tok — pass `effort: 'medium'` or `'low'` when the user wants a faster, shallower pass). Invalid values fall back to the defaults.
- Optional `allowStale: true` — only meaningful with `resume: true`. A resume normally refuses to continue when the target changed since the review was checkpointed (the file was edited / the PR got new commits): the `error` message says the checkpointed Codex session is **stale** and shows the saved vs current content id, because the saved session reviewed the OLD content and replaying critiques against it would be misleading. Pass `allowStale: true` to continue anyway (the user accepts the mismatch), or re-run without `resume` for a fresh review.
- Optional `--comment` flag (or the user saying "post it to the PR" / "comment on the PR") → pass `comment: true`. **PR targets only** — it posts the synthesized result as ONE summary comment (confirmed findings + the disputed set + prioritized actions), created once and then **updated in place** on re-run via a hidden marker (no duplicate comments). Ignored with a note for file targets. Opt-in, off by default — this is the only write the workflow makes to GitHub.

Then call (omit `effort` to take the default; add `comment: true` only when the user opted in):
Workflow({ name: 'adversarial-review', args: { target: '<parsed-target>', maxRounds: 3 } })

Invoke by **`name`**, not a relative `scriptPath` — `name` resolves the engine cwd-independently from `~/.claude/workflows/adversarial-review.js` (synced there by the plugin's `SessionStart` hook from its bundled `workflows/`) or a project `.claude/workflows/`. A relative `scriptPath` would resolve against the user's current project and fail in any repo that doesn't have its own copy. If `name` can't be found, the engine wasn't synced (hooks disabled, or first session before the hook ran) — tell the user to restart Claude Code, or to run the README's fallback `curl … -o ~/.claude/workflows/adversarial-review.js`.

After the workflow completes, format and present the result based on `status`:
- `agreed` — both agents converged. Show summary, agreedFindings (severity + confidence + citation + action item — include any `refuterNote` annotations), and prioritizedActionItems.
- `needs_approval` — hit the round cap without full agreement. Show the synthesized findings + unresolvedPoints, then surface the permission gate: ask the user whether to approve more rounds. If yes, re-invoke with `{ target, resume: true, maxRounds: <higher> }` (this CONTINUES from the saved checkpoint, it does not restart).
- `needs_human` — a question only the user can answer. Surface `question` + `context` clearly and stop. When they answer, re-invoke with `{ target, resume: true, humanAnswer: "<answer>" }`.
- `codex_failed` — Codex failed to produce a review (the workflow already auto-retried once for plausibly-transient failures). The message carries a tail of Codex's stderr when one was captured — show it, it usually names the real cause (auth, network, model). Special case: if Codex was still running when the ~60-minute poll budget expired (rc 124), the message suggests re-running with a lower `effort` instead of retrying — a second run at the same effort hits the same wall. Otherwise offer to re-run (fresh, or `resume: true` if state was saved).
- `resume_failed` — the Codex session id wasn't captured so the loop couldn't continue. Report it; offer a fresh re-run.
- `error` — bad/missing target, invalid file path, or a stale resume (see `allowStale` above). Show the message.

Every `agreed`/`needs_approval` result also carries `citationAudit` `{ checked, unresolved, results[] }`: each `file:line` cited in the findings is checked against the repo (file exists + line in range; bare filenames resolved via `find`; for PR targets the check runs against the PR head worktree when available). When `unresolved > 0`, call it out prominently and tell the user those citations are stale or hallucinated and must be re-checked before acting (the message field already appends this warning). Each `ok` result additionally carries `detail` = the first ~200 chars of the cited line's actual text, so a human can eyeball whether the line plausibly supports the finding — surface it alongside the finding. Note the check confirms the line *resolves*, not that it says what the finding claims — line-in-range ≠ line-correct; the `detail` text is what makes that eyeball check cheap.

Results may also carry `refutation` `{ checked, refuted, skipped }` — the post-synthesis refuter pass. Each agreed finding (up to 12, most severe first; the rest count as `skipped`) is handed to a fresh-context skeptic that never saw the debate transcript and actively tries to refute it against the source. High/medium-confidence refutations move the finding OUT of agreedFindings into unresolvedPoints (carrying the contrary evidence, so it renders as disputed); low-confidence doubts keep the finding but annotate it with a `refuterNote`. When `refuted > 0`, call it out — two models agreeing is not truth, and the refuters found specific contrary evidence.

When `comment: true` was passed (PR only), the result also carries `comment` `{ posted, action, url }`. Surface the comment URL when `posted` is true; if `posted` is false, tell the user it did not post (gh failure or missing permission) — the findings in the result still stand regardless. A post failure does NOT change the review `status`. In the posted comment, audit-confirmed `file:line` citations render as clickable GitHub permalinks pinned to the reviewed head commit (unverified refs stay as plain text — a permalink would lend them false credibility), and findings with a `refuterNote` get a 🛡️ sub-line.

Notes:
- Codex runs as the workflow's default model (named once in the model/effort bullet above); reasoning effort defaults to `high`. Both are overridable per run via the `model`/`effort` args.
- Round 1 is **blind and parallel**: while Codex produces its initial review, a Claude agent independently reviews the same target with the same rubric WITHOUT seeing Codex's output, so the loop's later "what did Codex miss" hunt starts from an unanchored frame instead of being primed by Codex's. If the blind pass fails, the review degrades gracefully to a Codex-only round 1.
- Codex runs via a **launch → poll → harvest** protocol: the run is launched detached and polled with short probes, so a review has **no 10-minute Bash-timeout ceiling**. The poll budget is ~60 minutes of Codex runtime; exhausting it surfaces as `codex_failed` with the lower-`effort` suggestion (rc 124, never auto-retried). All other Codex failures get ONE automatic retry before failing.
- **PR targets review the PR head**, not the current checkout: the head commit is fetched into a reusable worktree under `~/.claude/adversarial-review-state/worktrees/`, and Codex's context reads plus the citation audit run there. When the worktree can't be created (fetch failure, detached environments) the review falls back to the current checkout with a logged warning — citations may then falsely resolve or falsely fail if the PR branch isn't checked out. Worktrees untouched for 14 days are pruned; state checkpoints older than 30 days likewise.
- State persists to ~/.claude/adversarial-review-state/ so `resume: true` genuinely continues a paused review rather than starting over (subject to the staleness guard above).
- The Bash permissions the Codex subagent needs are shipped in this plugin's `settings.json` and applied when the plugin is enabled, so the auto-mode safety classifier doesn't block it: `Bash(codex exec:*)`, plus `Bash(nohup sh -c:*)` and `Bash(disown:*)` for the detached launch (`nohup sh -c` is the exact literal prefix of the launch command — the wrapped body only ever runs `codex exec`, and phrasing the grant that narrowly avoids a blanket `nohup` rule), `Bash(mktemp:*)`, `Bash(rm -f:*)` and `Bash(rmdir:*)` (run-dir cleanup deletes the four known run files then `rmdir`s — deliberately NOT `rm -rf`, so no standing recursive-delete grant ships), `Bash(mkdir -p:*)`, the git probes `Bash(git rev-parse:*)`, `Bash(git fetch:*)`, `Bash(git worktree:*)` (PR-head worktree), `Bash(git hash-object:*)` (staleness content id), the poll loop's `Bash(sleep:*)`/`Bash(seq:*)`/`Bash(test:*)`, the read/format utilities the generated bash runs — `Bash(find:*)`, `Bash(grep:*)`, `Bash(cat:*)`, `Bash(sed -n:*)`, `Bash(cut:*)`, `Bash(awk:*)`, `Bash(wc:*)`, `Bash(tail:*)`, `Bash(printf:*)`, `Bash(shasum:*)` — and the scoped `gh` prefixes `Bash(gh pr view:*)`, `Bash(gh pr diff:*)`, `Bash(gh pr comment:*)`, `Bash(gh repo view:*)`, `Bash(gh api:*)` — deliberately NOT a blanket `Bash(gh:*)`: these grants apply to every session while the plugin is enabled, so they stay as narrow as the workflow allows (no `gh pr merge`, `gh repo delete`, `gh secret`, …). One deliberate gap: the preflight's 14-day worktree housekeeping has a rare `rm -rf` fallback for a worktree `git worktree remove` can't delete — that may prompt for permission rather than being pre-granted. If `codex exec` is still blocked (e.g. the plugin isn't enabled), add these to `.claude/settings.local.json` and re-run.
- With `comment: true`, the post step additionally runs `gh repo view`, `gh api` (list + PATCH the comment), and `gh pr comment` to create/update the summary comment. These need the usual `gh` auth (repo write scope) and are covered by the scoped `gh` permissions above.
